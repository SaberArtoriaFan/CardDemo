# 卡牌对战网页原型 MVP 说明

## 目标

这份文档用于约束第一版 HTML 网页原型的开发范围，目标不是做完整游戏，而是尽快验证以下三件事：

1. `充能 / 攻击 / 防御` 三种基础动作是否能形成稳定、有趣的博弈。
2. 能量跨回合保留后，是否会自然形成攒资源与爆发时机的决策。
3. 场上牌序与结算顺序，是否真的能带来策略深度，而不是单纯堆数值。

第一版原型应优先验证玩法，不追求内容量、美术完整度或长期养成系统。

## 产品定位

- 类型：双人同时出牌的回合制卡牌对战
- 核心卖点：同时决策、顺序结算、预判博弈、能量管理
- 首版形式：本地网页 Demo
- 优先模式：玩家对简单 AI，或本地双人共用一台设备

## 本次 MVP 范围

MVP 只做最小可玩闭环，包含以下内容：

- 双方生命值
- 双方能量值
- 三种基础牌：`充能`、`攻击`、`防御`
- 少量词条
- 最多六张的场上队列
- 双方确认后自动结算
- 完整结算日志
- 一局可从开始打到分出胜负

本次 MVP 不做以下内容：

- 牌堆构筑
- 遗物系统
- 多角色成长
- 敌人卡背情报系统
- 大量功能牌
- 联机
- 美术资源生产管线
- 复杂动画

## 核心玩法概述

双方围绕一个最多六张牌的结算队列进行博弈。每回合双方同时进行操作，确认后从前往后依次结算牌的效果。生命值先归零的一方失败。

每张牌由三部分组成：

- 类型：`充能` / `攻击` / `防御`
- 消耗：打出或结算该牌所需的能量
- 词条：在打出时或结算时触发的特殊效果

能量可跨回合保留，这意味着玩家可以选择短期应对，也可以为后续高强度攻击做准备。

## 推荐的 MVP 回合结构

为了降低首版复杂度，建议采用下面这套回合结构：

1. 双方各执行一个操作。
2. 可执行的操作为：`放置一张牌`、`调整一张牌顺序`、`替换场上一张牌`。
3. 双方确认后，开始本回合结算。
4. 按场上队列从前到后依次结算牌。
5. 结算结束后，检查生命值是否归零。
6. 若未分出胜负，进入下一回合。

## 更稳妥的首版简化

为了更快验证玩法，建议第一版进一步收缩：

- 场上仍保留最多六格
- 第一版只允许将新牌放到末尾
- 第一版可以不开放任意插入
- 第一版可以不开放“替换场上一张牌”
- 第一版只保留“每回合可新增一张牌”与“可移动一张已有牌一格”中的一种

如果想把开发风险压到最低，建议第一轮先采用下面这个版本：

1. 每回合双方只能选择打一张新牌到队列末尾。
2. 双方确认后，从前到后结算全部场上牌。
3. 结算后的牌移除。
4. 保留生命、能量和日志。

等基础博弈成立后，再加入插入、换位和替换机制。

## 基础规则建议

以下规则建议作为首版默认实现，方便先形成一个可测版本。

### 生命值

- 双方初始生命值：`20`

### 能量

- 双方初始能量：`0`
- 能量可跨回合保留
- 若规则未特别说明，能量不足时不可打出对应牌

### 充能

- `充能`牌基础效果：获得 `1` 点能量
- 若该次结算被对方攻击命中，则自己失去对应生命值

### 攻击

- `攻击`牌有一个能量消耗值
- 该牌攻击强度通常等于其消耗的能量值
- 打出该牌时需支付消耗

### 防御

- `防御`牌基础效果：若对方该位置为攻击，则免疫这次攻击伤害
- `防御`默认不造成伤害

## 对位结算建议

第一版建议按“同序号对位”理解当前轮次的主要交互，即双方队列在同一结算位置的两张牌相互作用。

### 充能 vs 攻击

- 充能方获得 `1` 能量
- 充能方受到攻击伤害

### 充能 vs 防御

- 充能方获得 `1` 能量
- 防御方正常结算防御牌，但没有挡到伤害

### 充能 vs 充能

- 双方各获得 `1` 能量

### 攻击 vs 防御

- 防御方免疫此次攻击伤害

### 攻击 vs 充能

- 充能方受到攻击伤害

### 攻击 vs 攻击

这是当前方案里最需要明确的一条。MVP 建议先采用下面这个版本：

- 双方比较攻击强度
- 攻击强度高的一方视为本次对攻胜利
- 失败方失去等同于对方攻击强度的生命值
- 若攻击强度相同，则双方各失去等同于本次攻击强度的生命值

这样处理的好处是直观，日志也容易解释。

### 防御 vs 防御

- 默认无事发生

## 词条设计原则

首版词条不要追求花哨，优先满足以下标准：

- 一眼能懂
- 日志容易描述
- 不依赖复杂时序
- 不会大幅改写整套规则

## 首版推荐词条

建议第一版只做 2 到 3 个词条。

### 攻击词条

#### 强势

- 效果：若对方同位置也是攻击，则本次攻击强度 `+1`
- 目的：强化对攻博弈，制造“硬吃对攻”的可能性

### 防御词条

#### 回收

- 效果：若对方同位置不是攻击，则获得 `1` 点能量
- 目的：减少纯防御空过时的挫败感

### 功能词条

#### 洞察

- 效果：查看对手下一张待结算牌的类型，或查看对手牌池中的下一张牌
- 目的：强化心理博弈和情报价值

## 暂缓加入的词条

以下词条建议放到第二轮验证后再加：

### 反击

- 问题：它会改变攻击命中的后果，属于高影响词条
- 风险：容易让防御牌强度突然跳高

### 火车

- 问题：它会直接改动结算顺序
- 风险：如果基础结算逻辑还没稳定，调序词条会放大所有规则歧义

## 当前需要尽快钉死的规则问题

在正式开工前，以下规则最好先明确：

1. 攻击牌的可选消耗范围是多少，例如 `1` 到 `3`，还是动态任意值。
2. 充能牌是否永远固定只加 `1` 点能量。
3. 防御牌是否需要消耗能量，还是零费。
4. 双方攻击相等时，是否一定双输。
5. 词条分为“打出时触发”和“结算时触发”后，谁先结算。
6. 洞察查看的是“对手牌堆顶”还是“对手场上下一张待结算牌”。

如果暂时不想花太多时间做规则设计，建议先采用以下默认值：

- 攻击牌可选消耗：`1 / 2 / 3`
- 充能固定获得：`1`
- 防御消耗：`0`
- 对攻相等：双方都受伤
- 首版只做“结算时触发”词条
- 洞察查看：对手场上下一张待结算牌

## UI 原型建议

HTML 原型第一版只需要把信息表达清楚，不需要做复杂演出。建议页面包含以下区域：

- 左侧或上方：敌方信息区
- 右侧或下方：玩家信息区
- 中央：双方场上队列
- 底部：玩家可操作牌区
- 侧边或底部：结算日志区
- 显眼位置：当前回合数、生命值、能量值、确认按钮

### 必要信息展示

- 玩家生命值
- 玩家当前能量
- 敌方生命值
- 敌方当前能量
- 当前场上每张牌的类型
- 当前场上每张牌的消耗
- 当前场上每张牌的词条
- 当前回合日志

### 建议交互

- 点击手牌可选择打出
- 点击场上牌可查看详情
- 若允许换位，则通过按钮或选中后交换位置完成
- 点击“确认”后进入自动结算
- 结算日志逐条显示，方便回看

## AI 建议

第一版 AI 不要复杂，能稳定陪测就够了。可以先用简单规则：

- 能量为 `0` 时，优先使用充能
- 能量较高时，有概率使用高消耗攻击
- 若预测玩家可能攻击，则提高防御概率
- 偶尔随机，避免行为过于机械

首版 AI 的目标不是聪明，而是让玩家能快速打多局、观察系统是否有趣。

## 开发顺序建议

推荐按下面顺序推进：

1. 搭出最基础的单页 HTML 结构
2. 实现双方生命值、能量值与回合数显示
3. 实现三种基础牌的数据结构
4. 实现场上队列与出牌逻辑
5. 实现确认后自动结算
6. 实现结算日志
7. 补充简单 AI
8. 加入 2 到 3 个基础词条
9. 试玩并记录问题
10. 再决定是否加入插入、换位、替换和更多功能牌

## 验证重点

试玩时重点观察以下问题：

1. 玩家是否愿意为了后续爆发而先充能。
2. 防御是否过于保守或无脑。
3. 对攻结果是否直观、是否刺激。
4. 队列顺序是否真的带来策略，而不是徒增理解成本。
5. 词条是否让局面更有趣，而不是更难读。
6. 一局时长是否合适，是否能在几分钟内打完。

## 成功标准

如果第一版 Demo 达到以下状态，就说明可以进入下一轮迭代：

- 玩家可以独立完成一整局
- 规则不需要频繁口头解释
- 日志足以帮助理解每一步结算
- 基础三牌已经能产生明显博弈
- 玩家在试玩后会自然提出“如果再加一种牌会更好玩”的想法

这意味着核心系统成立，后续才值得继续叠加牌堆构筑、遗物和 PvE 信息差设计。

## 下一步建议

按照这份文档开工时，建议先做一个极简版本：

- 固定生命值与能量值
- 只有基础三牌
- 攻击只提供 `1`、`2`、`3` 三种消耗模板
- 先不做复杂词条
- 先跑通完整对局

只要这个版本已经能让人连续玩上几局，再开始扩内容，开发节奏会更稳。

## 开发任务清单

这一节用于把 MVP 拆成可以直接执行的开发 TODO。

### 阶段 1：项目骨架

目标：先把页面和脚本跑起来，不处理复杂规则。

- 创建 `index.html`
- 创建 `style.css`
- 创建 `main.js`
- 在页面中划分敌方区、中央战场区、玩家区、操作区、日志区
- 先放静态占位数据，确认布局可读

阶段完成标准：

- 浏览器打开后能看到完整页面骨架
- 主要区域位置明确
- 不依赖真实逻辑也能看出后续信息会放在哪里

### 阶段 2：基础状态系统

目标：先把游戏运行所需的状态集中管理起来。

- 定义游戏总状态对象
- 定义玩家状态对象
- 定义卡牌对象
- 定义日志对象
- 定义回合推进函数
- 提供初始化对局函数

阶段完成标准：

- 可以通过一份初始数据生成完整对局状态
- 可以在控制台打印当前回合、双方生命、能量、场上牌

### 阶段 3：基础渲染

目标：让页面根据状态真实显示。

- 渲染敌方生命值和能量
- 渲染玩家生命值和能量
- 渲染双方场上队列
- 渲染玩家可用操作牌
- 渲染回合数
- 渲染日志区

阶段完成标准：

- 修改状态后，页面能重新反映最新数据
- 基础牌信息能完整显示：类型、消耗、词条

### 阶段 4：出牌交互

目标：完成玩家一回合的基础操作。

- 支持点击一张可用牌
- 支持将牌加入玩家队列末尾
- 检查能量是否足够
- 打出后更新当前回合待确认状态
- 提供取消选择或重选能力
- 提供确认按钮

阶段完成标准：

- 玩家能在界面上完成一次合法出牌
- 非法操作会被拦住并提示原因

### 阶段 5：AI 行为

目标：让敌方能自动完成选择。

- 根据当前能量生成 AI 可选动作
- 写最简单的决策规则
- 在玩家确认后锁定 AI 动作
- 将 AI 选择写入敌方队列

阶段完成标准：

- 玩家每次确认后，敌方都能给出有效动作
- 不会出现 AI 选择了能量不足的牌

### 阶段 6：结算系统

目标：跑通一整轮从确认到结果的自动处理。

- 读取双方当前队列
- 按顺序取出同位置牌进行对位计算
- 结算基础类型效果
- 应用伤害、能量变动与词条效果
- 将本次事件写入日志
- 检查胜负
- 推进到下一回合

阶段完成标准：

- 点击确认后能自动完成整轮结算
- 生命、能量、日志都会同步更新

### 阶段 7：词条系统

目标：在不破坏主流程的前提下加入扩展能力。

- 实现 `强势`
- 实现 `回收`
- 预留 `洞察` 的数据字段和展示位置
- 统一词条触发入口

阶段完成标准：

- 词条效果能在日志中清晰体现
- 没有词条的牌也能正常走同一套结算流程

### 阶段 8：对局收尾与复盘

目标：让 Demo 具备基本可玩性和可测试性。

- 显示胜负结果
- 提供重新开始按钮
- 保留本局完整日志
- 记录简单平衡性观察

阶段完成标准：

- 一局结束后玩家知道为什么赢或输
- 可以快速重开继续试玩

这一节不是视觉定稿，而是信息布局建议。

3. 中央结算队列区

### 区域职责建议

#### 顶部信息栏

- 显示回合数
- 显示当前阶段，例如 `等待出牌`、`结算中`、`对局结束`
- 提供重新开始按钮

#### 敌方状态区

- 显示敌方生命
- 显示敌方能量
- 显示敌方队列
- 若未来加入情报玩法，可在这里显示已知情报

#### 中央结算区

- 当前不必复杂
- 可以只用来高亮“正在结算第几组牌”
- 后续再加入动画

#### 玩家状态区

- 显示玩家生命
- 显示玩家能量
- 显示玩家当前已布置的队列

#### 玩家操作区

- 显示本回合可选牌
- 显示当前选中的牌
- 显示能量不足提示
- 放确认按钮

#### 日志区

- 记录所有关键事件
- 最新日志置顶或滚动到底部
- 每条日志尽量短句化

## 页面交互拆分

为了避免前端逻辑过早打结，建议把交互拆成下面几种状态。

### 状态 1：等待玩家选择

- 玩家可以点击操作牌
- 玩家可以查看场上牌详情
- 不进行结算

### 状态 2：等待玩家确认

- 玩家已选择本回合动作
- 玩家可取消并重选
- 玩家点击确认后锁定本回合选择

### 状态 3：敌方已确认，准备结算

- 页面禁止继续更改操作
- 显示敌方已准备完成

### 状态 4：自动结算中

- 逐条播放日志
- 高亮当前结算位置
- 暂时禁用按钮

### 状态 5：回合结束或对局结束

- 若未结束，则进入下一回合
- 若结束，则显示胜负与重开按钮

## 数据结构设计建议

这一节以原生 HTML + JavaScript 为前提，故意保持简单。

### 游戏状态对象

```js
const gameState = {
  turn: 1,
  phase: "player-select",
  winner: null,
  player: {},
  enemy: {},
  logs: [],
  resolution: {
    currentIndex: null,
    pendingEvents: [],
  },
};
```

字段说明：

- `turn`：当前回合数
- `phase`：当前流程阶段
- `winner`：胜者，未结束时为 `null`
- `player` / `enemy`：双方状态
- `logs`：完整日志
- `resolution`：当前结算过程所需的临时数据

### 玩家状态对象

```js
const sideState = {
  id: "player",
  hp: 20,
  energy: 0,
  queue: [],
  handOptions: [],
  selectedAction: null,
  revealedInfo: [],
};
```

字段说明：

- `hp`：生命值
- `energy`：当前能量
- `queue`：场上待结算队列
- `handOptions`：本回合可选择的牌模板
- `selectedAction`：本回合已选择但尚未结算的操作
- `revealedInfo`：洞察等效果带来的公开信息

### 卡牌对象

```js
const card = {
  id: "atk-2-001",
  name: "攻击 2",
  type: "attack",
  cost: 2,
  power: 2,
  keywords: ["strong"],
  timing: "resolve",
  meta: {},
};
```

字段说明：

- `id`：唯一标识，便于日志与渲染
- `name`：显示名称
- `type`：`charge` / `attack` / `defend`
- `cost`：能量消耗
- `power`：攻击强度或主要数值
- `keywords`：词条列表
- `timing`：默认触发时机
- `meta`：扩展字段

### 动作对象

如果首版只支持“打到末尾”，动作对象可以很轻。

```js
const action = {
  type: "play-card",
  actor: "player",
  cardId: "atk-2-001",
  targetIndex: 2,
};
```

后续若加入换位、替换，可以扩成：

```js
const actionSwap = {
  type: "move-card",
  actor: "player",
  fromIndex: 3,
  toIndex: 2,
};
```

### 日志对象

```js
const logEntry = {
  turn: 1,
  step: 3,
  type: "resolve",
  text: "玩家的攻击 2 命中敌方充能，造成 2 点伤害。",
};
```

这样做的好处是：

- 既能直接渲染文本
- 又保留结构化字段，后续方便筛选、回放、调试

## 结算流程拆分

建议将结算写成几个小函数，而不是一个超长函数。

### 推荐函数列表

- `createGame()`
- `getAvailableCards(sideState)`
- `selectPlayerAction(cardKey)`
- `confirmTurn()`
- `chooseEnemyAction(gameState)`
- `resolveTurn(gameState)`
- `resolvePair(playerCard, enemyCard, gameState, index)`
- `applyCardKeywords(context)`
- `appendLog(entry)`
- `checkWinner(gameState)`
- `render(gameState)`

### 推荐结算顺序

1. 锁定双方本回合动作
2. 将新牌放入队列
3. 从索引 `0` 开始读取双方同位置牌
4. 先计算基础类型对位结果
5. 再应用词条修正
6. 写入生命与能量变化
7. 写入日志
8. 继续下一个位置
9. 全部完成后检查胜负
10. 切换到下一回合

## 结算上下文建议

为了让词条系统更容易扩展，建议在每组对位时创建一个临时上下文对象。

```js
const resolveContext = {
  turn: 1,
  index: 0,
  playerCard,
  enemyCard,
  playerDamage: 0,
  enemyDamage: 0,
  playerEnergyDelta: 0,
  enemyEnergyDelta: 0,
  notes: [],
};
```

这样后续无论是 `强势` 还是 `回收`，都只是在这个上下文上加减数值或写注释。
